# 生产规则总表

最后更新：2026-09-03

这份文档是当前项目的正式生产规则。以后凡是改市场总览、市场监控、自选股、股票池、质量检查相关逻辑，都先改这份文档，再改代码。

## 1. 总原则

1. 先定义规则，再写实现。
2. 每个模块必须先明确四件事：
   - 显示什么
   - 什么时候刷新
   - 读哪个正式数据源
   - 出问题时怎么判断是哪一层坏了
3. 不允许在前端或 API 读取层偷偷补旧值、补缺列、补缺字段。
4. 不允许为了“先显示出来”叠加隐藏机制。
5. 问题只能归到三层之一：
   - 数据源/产物问题
   - 刷新机制问题
   - 显示规则问题

## 2. 一页式模块规则表

| 模块 | 页面正式读取 | 正式数据源 | 正式生产链路 | 刷新规则 | 前端职责 | 明确禁止 |
|---|---|---|---|---|---|---|
| 市场情绪 / 短线情绪 / 板块资金 / 成交额榜 | 实时接口 | 实时 API | 实时请求 | 低频实时，够用即可 | 正常展示、不要阻塞首屏 | 不要和盘后慢链路绑死 |
| 市场监控详情 | `GET /api/market-monitor` | 本地 `market-monitor/data/` | 本地盘后生产后由后端直读母表 | 交易日 15:20 后更新一次 | 按后端结果展示 | 不要再读旧 published bundle |
| 百亿成交行业分布 | `hot_stock_matrix` | 本地 `market-monitor/data/history/hot_stocks.csv` | 本地市场生产 + `report_data` 构造 | 交易日 15:25 后更新一次 | 只按矩阵渲染 | 前端禁止自算矩阵 |
| 申万行业 / 四行业拥挤度 / 创新药 | `GET /api/market-monitor` | 本地 `market-monitor/data/` | 本地盘后生产后由后端直读母表 | 交易日 15:20 后更新一次 | 只展示正式结果 | 不准页面层修数 |
| 自选股 / 股票池展示 | `GET /api/stock-pool` | 本地 `pool.json` + 本地 `stocks.csv` | 常驻后端直接请求 API | 交易日 15:25 后更新一次 | 定义与当天缓存直接合并展示 | 不准读取时回填旧 20 日 / YTD |
| 股票池标的定义 | 后端读写本地 `pool.json` | `data/stock-pool/pool.json` | 人工维护 + 同步 GitHub 备份 | 有增删时即时同步 | 提供增删入口 | 本地优先；不承担行情日期 |
| 关注列表 | 后端读写本地 `pool.json.focus` | `data/stock-pool/pool.json` | 实时保存 + 同步 GitHub 备份 | 用户操作即更新 | 只管理关注代码 | 本地优先；不承担行情结果生产 |
| 数据质量模块 | `GET /api/market-monitor` 中的 quality | 母表状态 + 前端可显示性检查 | 本地市场生产 | 盘后随市场母表更新 | 友好展示结果 | 不直接吐原始 JSON 给你看 |

市场母表在本机交易日盘后生产；非交易日不写空值。生产成功后才备份到 GitHub，网页始终读取本地正式母表。

### 正式来源优先级

1. 东方财富是市场监控中全 A、四行业拥挤度、创新药和百亿成交的正式行情来源。
2. Choice 历史修复属于东方财富体系，仅用于明确的历史补数。
3. 腾讯、同花顺等仅可在上述市场监控数据的东方财富当天不可用时临时补位；母表必须写明“临时回退，待东方财富覆盖”。自选股是独立日更缓存，可按其自身稳定 API 取数。
4. 临时值不能覆盖已有东方财富/Choice 正式值；东方财富恢复后，同日重跑必须覆盖临时值。

## 3. 市场总览与市场监控

### 3.1 规则

1. 市场总览分成两类内容：
   - 实时模块
   - 盘后模块
2. 实时模块包括：
   - 市场情绪
   - 短线情绪
   - 板块资金
   - 部分成交额榜
3. 盘后模块包括：
   - 市场监控详情
   - 百亿成交矩阵
   - 申万行业
   - 四行业拥挤度
   - 创新药
   - 数据质量
4. 盘后模块统一从 `GET /api/market-monitor` 读取。
5. `GET /api/market-monitor` 的唯一正式母表目录是 `market-monitor/data/`。

### 3.2 刷新规则

1. 盘后模块由常驻本地后端在交易日 `15:25` 后更新一次。
2. 首页允许先显示实时模块，再补盘后模块。
3. 首页不允许为了等盘后模块，把实时模块一起卡住。

### 3.3 禁止事项

1. 不允许再引入旧的 published bundle 作为并行正式来源。
2. 不允许前端自己重组市场监控历史结果。
3. 不允许无说明地改市场监控详情的展开/折叠交互。

## 4. 百亿成交行业分布

### 4.1 显示规则

1. 弹窗只显示后端已经生成好的 `hot_stock_matrix`。
2. 列顺序固定为最近 10 个有记录的交易日。
3. 最新日期固定在左侧。
4. 前端只负责按矩阵渲染，不负责业务计算。

### 4.2 数据规则

1. 正式历史源是 `market-monitor/data/history/hot_stocks.csv`。
2. 后端在 `report_data` 构造阶段生成 `hot_stock_matrix`。
3. 页面正式读取来源只有 `/api/market-monitor` 返回的 `hot_stock_matrix`。

### 4.3 排障顺序

如果像 `2026-08-24`、`2026-08-25` 这种日期没显示，只按下面顺序查：

1. `hot_stocks.csv` 有没有这两天。
2. `hot_stock_matrix` 生成结果里有没有这两天。
3. 当前网页后端是否还在返回旧日期。
4. 前端是否拿到了旧运行态结果。

### 4.4 禁止事项

1. 前端禁止根据 `hot_stocks_history` 自己重算矩阵。
2. 不允许点开弹窗时再刷新矩阵。
3. 不允许为了补显示临时补列头。

## 5. 申万行业 / 四行业拥挤度 / 创新药

1. 这几块都属于 market monitor 正式盘后模块。
2. 统一由常驻本地后端盘后生产，GitHub 只保存成功后的备份。
3. 统一从 `market-monitor/data/` 母表生成。
4. 页面只展示正式结果。
5. 如果缺天、缺字段、值不合理，修生产脚本或母表，不在前端打补丁。

## 6. 自选股 / 股票池

### 6.1 规则定位

1. 自选股不是 market monitor 母表模块。
2. 自选股也不是“网页打开时现场爬一遍完整结果”。
3. 自选股展示直接合并本地池子定义与每日一次的本地行情缓存。

### 6.2 数据职责

1. `data/stock-pool/pool.json` 只负责定义池子里有哪些标的。
2. `data/stock-pool/pool.json` 同时保存：
   - 核心股票池定义
   - 近期关注代码列表
   - 研究篮子定义
3. 股票池不再维护额外 bundle；页面只读取本地定义和本地行情缓存。

### 6.3 刷新规则

1. 常驻后端是自选股唯一正式日更链路，独立于市场总览任务。
2. 在交易日 `15:25` 后运行一次。
3. 后端通过 API 拉取当日需要的数据；只有 162 只快照完整时才覆盖本地当天行情缓存。
4. 前端和后端读取本地 `pool.json` 与当天 `stocks.csv` 展示。
5. `pool.json` 不回写日度行情字段，只维护定义层。

### 6.4 页面显示范围

自选股页展示的这些内容都应该来自本地定义与当天行情缓存：

1. `stocks`
2. `indices`
3. `heatmap`
4. `leaders`
5. `20日`
6. `YTD`
7. 强弱矩阵
8. 最强最弱榜

### 6.5 分类规则

1. 页面主筛选顺序固定为：
   - 近期关注
   - 研究篮子
   - 行业分类
2. 研究篮子是主要使用分类，不额外加表格列标签。
3. 行业分类保留，但作为次级筛选入口。
4. 研究篮子只属于定义层，不参与日度行情计算逻辑。

### 6.6 禁止事项

1. 不允许把自选股并入 market monitor 母表直读链路。
2. 不允许在 `/api/stock-pool` 返回时用历史缓存补当天缺失字段。
3. 不允许前端为了显示完整榜单自行补算业务字段。
4. 如果当天缓存缺字段，修 `daily_stock_pool` 生产脚本，不修读取层。

## 7. 数据质量模块

### 7.1 目标

数据质量模块不应该展示底层开发字段，而应该直接回答三个问题：

1. 今天各模块有没有更新到位。
2. 母表和前端是否都能正常显示。
3. 有没有历史数据遗漏。

### 7.2 正式输出结构

1. 数据更新日期汇总
   - 每个模块最新有效日期
   - 是否到今天盘后日期
2. 前端可显示性检查
   - 母表是否齐
   - 前端是否能正常显示
   - 是否读到旧运行态
3. 历史遗漏检查
   - 是否缺交易日
   - 是否缺关键字段
   - 缺的是哪个模块、哪一天

### 7.2A 页面文案必须怎么说

1. 必须把“最新生产状态”和“历史完整性”拆开写。
2. 如果今天页面基准日已经正常，例如 `2026-08-31` 正常显示，但 `2026-08-28` 有历史缺口，页面必须明确写成类似：
   - 最新页面日期：`2026-08-31`，当前显示正常
   - 历史缺口：`2026-08-28` 缺 `申万行业 / 四行业拥挤度 / 创新药`
3. 不允许只给一排 `PASS`，让人误以为历史也完全没问题。
4. 也不允许只写 `WARN` 却不说明是哪一天、哪个模块有问题。

### 7.3 文案规则

1. “未解决事项”必须写成人能直接看懂的话。
2. 只有开发排障明细里才允许出现原始字段名。
3. 不再直接向页面输出一长串 JSON 或内部校验 key。

## 8. 统一排障顺序

以后所有生产问题，统一按下面顺序查：

1. 先看正式源有没有更新。
2. 再看生产任务有没有跑成功。
3. 再看后端接口当前实际返回什么。
4. 最后才看前端渲染。
5. 不允许一上来在显示层补逻辑。

## 8A. 故障修补流程

故障修补和日常生产是两条不同流程，必须分开。

### 8A.1 日常生产

1. `15:20` 后跑 market monitor 正式母表。
2. 市场总览与 stock-pool 在收盘后各自独立运行；任一失败不阻断另一条链路。
3. 页面分别读取：
   - 市场总览 / 市场监控：`market-monitor/data/`
   - 自选股：本地 `pool.json` + `stocks.csv`

### 8A.2 故障修补

1. 先确认缺的是哪张母表、哪一天。
2. 只补母表，不在前端硬补。
3. 补完后重新检查后端接口返回的日期和模块。
4. 如果当天页面仍不对，再查本地服务是否仍在读旧运行态。
5. Choice 恢复前，允许把缺口明确保留为“待补历史”，但不允许拿实时值冒充历史值。

## 9. Git 与代码治理

1. `main` 只保留当前正式生产方式需要的代码。
2. 已废弃的旧路径、旧 bundle 读取方式、旧 fallback 逻辑，能删就删。
3. 同一模块不允许长期并存两套正式读取逻辑。
4. 生产逻辑改动必须同步更新本文件。

## 10. 当前正式口径

1. 市场监控走唯一母表 `market-monitor/data/`。
2. 百亿成交弹窗只显示后端生成好的 `hot_stock_matrix`。
3. 自选股不并入 market monitor 母表。
4. 自选股展示直接读取本地定义和本机 API 生成的当天缓存；`daily_stock_pool.yml` 仅用于手动故障恢复。
5. `pool.json` 只管理标的、近期关注和研究篮子，不承担行情结果母表职责。
6. 重点维护的是：
   - 正式母表
   - 正式日更缓存
   - 刷新时间
   - 数据源正确性
7. 不再叠加补丁式生产逻辑。
